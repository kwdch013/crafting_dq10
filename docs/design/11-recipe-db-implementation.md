# レシピDB実装方針

## 目的

[レシピDB設計](./09-recipe-db-schema.md) を実装するにあたり、修正内容を難易度別に3段階へ分けます。

段階が上がるほど影響範囲と切り戻しの難しさが増します。段階1から順に進め、各段階の完了時点でアプリが動作する状態を保ちます。

## 全体の考え方

APIのレスポンス形式を現行JSONと同一に保つことで、段階2までフロントの修正を発生させません。
DBから現行JSON形式へ復元できることは、6職人70レシピで検証済みです ([レシピDB設計](./09-recipe-db-schema.md) の検証結果)。

フロントの修正が必要になるのは、レシピ登録の入口を画面からのPOSTに変える段階3だけです。

| 段階 | 難易度 | 対象 | フロント修正 | 切り戻し |
| --- | --- | --- | --- | --- |
| 1 | 低 | 追加のみ。既存の読み書き経路に触れない | なし | ファイル削除のみ |
| 2 | 中 | バックエンド内部の構造変更。APIの形式は不変 | なし | 事前エクスポート、環境変数変更、再起動 |
| 3 | 高 | 登録経路と分類の扱いを変更 | あり | 段階的な戻しが必要 |

## 段階1 (低): DB基盤の追加

既存の動作に一切影響しない追加だけを行います。この段階では、アプリは従来どおりJSONで動きます。

### バックエンド

| ID | 内容 | 完了条件 |
| --- | --- | --- |
| B1-1 | ベースイメージを `python:3.14-slim` へ変更し `psycopg[binary]` を追加。`docker-compose.yml` に `database_default` を外部ネットワークとして追加し、`.env` に `DATABASE_URL` を設定する | `api` コンテナから `postgres_db:5432` へ接続できる |
| B1-2 | `api/migrations/apply.py` を追加。`schema_migration` テーブルを作り、未適用のSQLを昇順にトランザクションで適用する | 4本のマイグレーションが適用でき、再実行しても二重適用されない。空のDBから70レシピが入る |
| B1-3 | 職人ごとのマッピング関数を追加。列展開の行と現行JSONの `items` 配列を相互変換する | DB接続なしで単体テストが通る |
| B1-4 | `api/scripts/import_recipes.py` を追加。現行JSONをDBへ投入する | 6職人70レシピが制約違反なく投入できる |
| B1-5 | ラウンドトリップテストを追加。現行JSON → DB → 復元が一致することを検証する | 全6職人で一致する |
| B1-6 | `api/scripts/export_seed.py` を追加。移行時点のスナップショットを `0004_seed_recipes.sql` として再生成できるようにする | 空のDBへマイグレーションを適用するだけで70レシピが入る |

### フロントエンド

修正はありません。

この段階で `craft_master` と職人別テーブルの対応は識別子付き外部キーで守られますが、見出しと職人別テーブルの行を必ずセットで書くことは投入スクリプトの責務です。
DDLで強制しない整合性は [レシピDB設計](./09-recipe-db-schema.md) を参照します。

### 難易度が低い理由

既存コードを変更せず、新しいファイルの追加だけで完結します。
問題が起きた場合は追加したファイルを消せば元に戻ります。
B1-3 は純粋な変換関数のため、DBを立てずにテストできます。

### 補足

マッピング関数は職人ごとに構造が違うため6種類必要ですが、鍛冶3職人は盤面サイズ以外が同一のため共通化できます。
分類テーブルの座標定義と、鍛冶のテンプレート分類の作成は B1-4 の責務です。

## 段階2 (中): 保存先の切り替え

`api/main.py` からデータアクセスを分離し、保存先をJSONとPostgreSQLで切り替えられるようにします。
APIのエンドポイントとレスポンス形式は変えないため、フロントの修正は発生しません。

### バックエンド

| ID | 内容 | 完了条件 |
| --- | --- | --- |
| B2-1 | `api/repository/` を追加し、`api/main.py` はHTTPの受け口だけにする。`json_store.py` は現行のファイル読み書きをそのまま移す | 既存のPythonテストが変更なしで通る |
| B2-2 | `postgres_store.py` に読み取りを実装する。`GET /api/recipes` は全職人を1往復で取得する | 現行JSONと同じ形式を返す |
| B2-3 | `RECIPE_STORE` 環境変数で保存先を切り替える (B2-5前の既定は `json`) | `postgres` 指定時にGET・PUT・DELETEが動作する |
| B2-4 | `api/scripts/export_recipes.py` を追加。DBから `recipes.json` と `recipes.js` を生成する | 出力がラウンドトリップテストと一致する |
| B2-5 | 既定を `postgres` へ変更し、`recipes.json` を `.gitignore` へ追加する | 画面が従来どおり動作する |

B2-5 の時点ではDBが真実源になりますが、ブラウザの `localStorage` に残るユーザー追加レシピはまだ取り込まれていません。
この期間は現行どおり `localStorage` の内容をAPI由来データへ重ねて表示し、取り込みは段階3cで行います。
[レシピDB移行設計](./08-recipe-db-migration.md) の Phase との対応も併せて参照します。

`recipes.json` を除外しても、初期化の入力は `0004_seed_recipes.sql` がコミット対象として残ります。

### フロントエンド

修正はありません。

書き込み (`PUT` / `DELETE`) は現行のインターフェースのまま、内部でDBへ反映します。
レシピIDは `craft_master.legacy_id` で引き当てるため、フロントが送る文字列IDをそのまま受けられます。

### 難易度が中程度の理由

既存の `api/main.py` (197行) の構造を変えますが、外部インターフェースが変わらないため既存テストで守れます。
切り戻し前にDBから `export_recipes.py` を実行してJSONを生成し、`RECIPE_STORE=json` を指定してAPIを再起動します。

一方で、6職人分の読み取り実装と、鍛冶の座標復元・調理の食材グループ復元など、職人ごとの分岐が入ります。
B2-2 が段階2の作業量の大半を占めます。

## 段階3 (高): 登録経路と分類の一元化

レシピ登録の入口を画面からのPOSTに変え、分類マスタをDB由来にします。
ここで初めてフロントの修正が発生します。

### 現状との差

| 項目 | 現状 | 移行後 |
| --- | --- | --- |
| レシピIDの発番 | フロントが `user-<職人>-<時刻>` を生成 | サーバーが `craft_master.id` を発番 |
| 真実源 | `localStorage` (API反映は補助) | DB (`localStorage` はオフライン時の控え) |
| 保存失敗時 | ブラウザには保存され、画面に残る | 保存されず、エラーとして扱う |
| 分類の選択肢 | `app/crafts/<職人>/config.js` の `recipeCategoryOptions` | DBの `*_category` テーブル |
| 鍛冶の使用マス | レシピごとに保持 | 分類が定義する |

### バックエンド

| ID | 内容 | 難易度の要因 |
| --- | --- | --- |
| B3-1 | `POST /api/crafts/{craftId}/recipes` を追加。サーバーがIDを発番し、登録結果を返す | 既存の `PUT` との併存期間の設計が必要 |
| B3-2 | 分類・特性・食材マスタの参照APIを追加する | 参照のみのため低め |
| B3-3 | 分類の新規作成APIを追加する。鍛冶では使用マスの座標を伴う | 盤面形状の入力方法を決める必要がある |

### フロントエンド

| ID | 内容 | 難易度の要因 |
| --- | --- | --- |
| F3-1 | レシピ保存を `PUT` (クライアント発番) から `POST` (サーバー発番) へ変更する | `app/main.js` のID生成 (3105行付近) と保存処理の書き換え |
| F3-2 | `localStorage` の位置づけをオフライン時の控えへ変更する | 保存失敗時の画面表示と、API優先ロジック (416行付近) の見直し |
| F3-3 | 分類の選択肢を `config.js` からAPI由来へ移す | 5職人の `recipeCategoryOptions` を段階的に置き換える |
| F3-4 | 鍛冶のレシピ追加で、分類選択に応じて使用マスを決める | 現行はレシピごとにマスを持つため、画面の流れが変わる |
| F3-5 | 既存の `localStorage` に残るユーザー追加レシピをDBへ移行する | 現行データに6件実在するため、初回起動時の取り込みが必要 |

### 難易度が高い理由

- 真実源が `localStorage` からDBへ反転するため、保存失敗時の挙動を決め直す必要があります。現状は「ブラウザには保存しました」と表示して続行しますが、DBが真実源になるとこの扱いは使えません。
- 鍛冶では分類が使用マスを決めるため、新しい盤面形状のレシピを追加するには分類の作成が先になります。現行の「レシピを追加すればよい」流れとは手順が変わります。
- `config.js` の `recipeCategoryOptions` とDBの分類テーブルが二重管理になるため、移行期間中はどちらを優先するかを決める必要があります。

### 段階3の分割

一度に進めず、以下の順で分けます。各段階の間でアプリは動作します。

1. 3a: マスタ参照APIの追加 (B3-2)。フロントは未使用のため影響なし。仕様は [マスタ参照API](./14-recipe-master-api.md)。
2. 3b: 分類の選択肢をAPI由来へ (F3-3、実装済み)。`config.js` はAPI停止時のフォールバックと表示順・テンプレートの引継ぎに残し、`legacyId` を持たない分類 (未分類・DB移行時の変換用テンプレート) は選択肢に出さず、分類の新規作成を扱う3dで扱う。
3. 3c: 登録経路をPOSTへ (B3-1、F3-1、F3-2、F3-5)。
4. 3d: 分類の新規作成と鍛冶の使用マス連動 (B3-3、F3-4)。

## テスト方針

| 段階 | テスト |
| --- | --- |
| 1 | マッピング関数の単体テスト (DB不要)、投入とラウンドトリップの結合テスト、空DBからのシード適用 |
| 2 | 既存のJSテスト65件とPythonテストが変更なしで通ること、`RECIPE_STORE` 両方での動作確認 |
| 3 | 登録・編集・削除の一連操作をブラウザで確認、保存失敗時の表示確認、既存 `localStorage` からの取り込み確認 |

段階2までは既存テストが回帰の防波堤になります。
段階3は画面の挙動が変わるため、既存テストの更新と、変更後の挙動に対する新規テストが必要です。

## 見送る項目

以下は本移行の対象外とし、DB移行の完了後に別issueで扱います。

- 単価、必要素材の個数、錬金素材のテーブル追加
- バザー価格の自動取得と損益計算
- 更新履歴テーブルと楽観ロック
