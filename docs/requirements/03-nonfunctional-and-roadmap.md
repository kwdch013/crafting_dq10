# 非機能要件と開発ロードマップ

## 性能

目標:

- 第8世代Core i7、GPUなしで実用動作
- キャプチャ更新は2から5fpsを標準とする
- 解析処理は1回あたり200ms以内を目標とする
- UI操作が重くならないこと

## 安定性

- DQ10ウィンドウが閉じられても落ちない
- 画面認識に失敗した場合は、前回値または未認識として表示する
- 認識値の信頼度を保持する
- 手入力で補正できる

## 拡張性

- 職人ごとに計算エンジンを分離する
- 画面認識と計算エンジンを分離する
- UIとロジックを分離する
- 調理MVPのあと、他職人を追加しやすい設計にする

## 安全性

- ゲーム操作を自動化しない
- DQ10のメモリを読み取らない
- 画面キャプチャとユーザー入力だけで動作する
- 外部通信を必須にしない

## オフライン動作

基本機能はオフラインで動作します。

Local LLMや外部APIは必須にしません。

## 技術方針

推奨技術:

- Web UI
- Docker / Docker Compose
- JavaScript
- OpenCV
- Tesseract OCR または Windows OCR
- mss / dxcam / Windows Graphics Capture

## レイヤー構成

```text
UI層
  職人選択、状態表示、設定、手入力補正

キャプチャ層
  DQ10ウィンドウ取得、画像切り出し、キャリブレーション

認識層
  OCR、ゲージ判定、テンプレート照合

職人エンジン層
  調理、鍛冶、裁縫など職人ごとの状態遷移と判定

評価層
  確定会心判定、おすすめ手、リスク評価

データ層
  職人データ、成功範囲、特技データ、設定保存
```

## 開発フェーズ

### Phase 1: 調理計算エンジン

- 手入力で現在値を入力
- 成功範囲との差分を表示
- ダメージ範囲を計算
- 確定会心候補を判定

### Phase 2: 調理UI

- Web UIを作成
- 職人種別選択を追加
- 各マスの状態を表形式で表示
- 手入力補正を可能にする

### Phase 3: キャプチャ

- DQ10ウィンドウ選択
- 画面キャプチャ
- 職人ミニゲーム領域の切り出し
- 手動キャリブレーション

### Phase 4: 画面認識

- 集中力OCR
- ゲージ判定
- 火力位置判定
- 認識信頼度表示

### Phase 5: おすすめ手

- 候補手を列挙
- 各候補手をシミュレーション
- リスクと期待値でスコア化
- 上位候補を表示

### Phase 6: 他職人拡張

- 職人共通インターフェースを定義
- 職人別設定を追加
- 必要に応じて職人別エンジンを追加
